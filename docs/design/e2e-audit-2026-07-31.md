### E10 — `bcc-middleware` signed every transaction for the wrong chain. *(critical, fixed)*

The real outage, and the one that mattered. Every chain write the middleware attempted
failed:

```
updateScore(0x360e…, 0) submission failed:
  The transaction declared chain ID 31337, but the connected node is on 84532
could not anchor 8 leaves for agent did:integrity:68fed1…:
  transaction submission failed: … -- retained in logs only
```

**Root cause — a missing env var, not the deployments file.** `bcc_middleware/app/config.py:37`
reads `CHAIN_ID` from the environment and defaults to `31337`. `oracle-backend` sets
`CHAIN_ID` in `docker-compose.yml`; **`bcc-middleware` never did.** So after the
2026-07-29 switch to Base Sepolia, it took `RPC_URL` from `DOCKER_RPC_URL` (→ 84532)
while its chain id stayed at the anvil default. web3 signs for the *declared* chain, so
the node rejected everything.

A second, independent misconfiguration sat behind it: `DEPLOYMENTS_FILE` was hardcoded
to `/deployments.local.json` with only that file mounted, so even once the chain id was
right the service would have used **anvil contract addresses on Sepolia**. Both are
fixed; both were needed.

Why this is the most serious item in this document: the failure was **silent and
self-directed**. The anchor path logs on failure and returns — "retained in logs only" —
so a protocol whose entire premise is anchored, non-forgeable evidence was failing to
anchor *its own construction*, for days, while every test passed and `/healthz` said
`ok`. That is precisely the class of gap the dogfooding mandate exists to catch.

**Verified fixed by on-chain state change** (2026-07-31). Env now reports `CHAIN_ID=84532
DEPLOY=/deployments.baseSepolia.json` and the chain-id error is gone — but that only shows
transactions are *submitted*. What shows they **succeed**:

| Evidence | Before | After |
|---|---|---|
| `StateAnchor.latestRoot` | `0xdecb860c63dae118…` | **`0x946387f7fab3a87c…`** |
| `isAnchoredRoot(0x946387f7…)` | — | **`true`** |
| `isAnchoredRoot(0xdecb860c…)` (append-only holds) | `true` | **`true`** |
| `pending_batch_size` | 2 | **0** (flushed) |
| `ReputationRegistry.scores(0x360e…).lastUpdated` | — | **`1785484478`** (this session) |

Nonce advancement (260 → 275) is corroborating only, and deliberately **not** treated as
proof: a reverting transaction consumes its nonce just the same.

Both roles were checked **before** the key was wired in, on two different contracts:
`hasRole(ANCHOR_ROLE, 0x67bA5D72…)` on the agent's `StateAnchor` (for `anchorRoot`) and
`hasRole(ORACLE_ROLE, …)` on its `ReputationRegistry` (for `updateScore`) — both `true`.

`BCC_MERKLE_BATCH_SIZE` is now surfaced in `docker-compose.yml`; setting it to 1 is what
made this provable with one real commitment instead of eight. That rarity is the point:
**the defect only manifests on flush**, which is why months of passing tests and an `ok`
healthz never surfaced it.

### E11 — The oracle serves stale anvil primitives as if authoritative. *(high)*

`GET /v1/agent/{did}` for an agent that does **not** exist on the configured chain
returns **200**, not 404, carrying anvil-era addresses and
`"blockchainAccountId": "eip155:31337:…"` — on an oracle configured for 84532. The only
signal that anything is wrong is `"primitives_source": "cache"`.

What happens: the chain read fails correctly (`resolveDID` reverts `UnknownDID()`), and
the handler falls back to the DB cache. Five DIDs registered against a local anvil before
the Sepolia switch are still in Postgres and still served this way.

The fallback is defensible on its own — a transient RPC failure should not blank the
dashboard. What is not defensible is that it is **chain-agnostic**: it will serve
addresses from a *different chain* without saying so. For a system whose stated invariant
is "the chain is the source of truth," a 200 carrying addresses that do not exist on the
configured chain is a false answer, not a degraded one. The cache should record the chain
id it was populated from and refuse to serve across a mismatch.

Do **not** fix this by deleting the five rows. That silences the symptom and destroys
evidence.

### E12 — An expected 404 is logged at `ERROR`. *(low, but it caused this whole audit)*

`chain.rs:550` logs every `resolveDID` revert at `ERROR`, and `error.rs:66` then maps
`AgentNotFound` to a correct **404**. So a *normal, correct* not-found response emits a
red `ERROR` line, repeated per poll. Hundreds of these lines are what made the service
look catastrophically broken and drove E1's "root cause undetermined."

The severity is genuinely low; the cost was not. A log level that does not distinguish
"this request asked for something that isn't there" from "this service is failing"
converts routine polling into an apparent outage.

### E13 — The nonce race survives its own documented lock. *(medium, unresolved)*

Observed live, after E10 was fixed:

```
updateScore(0x360e…, 0) submission failed:
  {'code': -32000, 'message': 'nonce too low: next nonce 261, tx nonce 260'}
```

`nonce_lock.py` documents this exact failure and holds a process-wide lock across the
full read → sign → broadcast → receipt sequence specifically to prevent it
(`PRODUCTION_GAPS.md` §5). It still happened.

The lock is process-wide, so an in-process race is unlikely to be the explanation.
The leading hypothesis is a **stale nonce read from the load-balanced public RPC** —
`contracts/.env` itself warns that `publicnode.com` rate-limits aggressively, and a
round-robin across nodes with inconsistent mempool views would produce exactly this.
**Explicitly unconfirmed**: distinguishing the two requires re-running against a
dedicated (Alchemy/Infura) endpoint. Recorded as a hypothesis, not a diagnosis.

### E14 — The vault-leaf importer would have written a false lineage. *(high, caught before it ran)*

`scripts/import_memory_dag.py` chained every vault leaf to its predecessor in
`leaves.jsonl` order. The handoff flagged the "file order == commit order" assumption as
untested. It is **half right, and the wrong half is load-bearing.**

Measured against the real 21-leaf vault:

- timestamps *are* strictly monotonic in file order — so file order is chronological ✅
- all 21 `commit_sha`s are distinct and present in git ✅
- but **chronological order is not ancestry**: of 20 consecutive pairs, **19 are true
  git ancestor pairs and one is not.** `6c0c9bf → d7e4deb` are *siblings* off merge-base
  `354c6b5`, one on `docs/spec-open-definitions` and one on `main`, because the developer
  switched branches.

Chaining linearly would have recorded a `derived_from` edge asserting that `d7e4deb`
descends from `6c0c9bf` when git says it does not. In a recall system that is a harmless
approximation; in an **evidence** system whose whole claim is non-forgeable lineage, a
lineage edge that is merely plausible is worse than no edge — it is a false statement
that verifies.

**Fixed before the first real run.** The importer now resolves each node's parent as the
most recent earlier leaf that is a genuine `git merge-base --is-ancestor` of it, and
falls back to a second root rather than inventing a parent. The corrected import records
`d7e4deb → 36e23d9b` (the true fork point) and leaves `6c0c9bf` as what it actually is:
an unmerged branch tip with no descendant.

Known limitation, recorded rather than papered over: `root_of_heads` is computed over
*named refs*, and only `head` is named — so it commits to the main line, not to the whole
frontier including unmerged tips.

### E15 — A test failure could never be recorded, and silently truncated the suite. *(critical, fixed)*

Found by the ordinary act of running `make test` with something actually broken —
which, on the evidence, had not happened in a long time. Every line of the `test`
target read:

```make
cd pkg && uv run pytest && cd .. && $(TEST_STATUS) pkg pass || $(TEST_STATUS) pkg fail
```

Two bugs compound here:

1. **A failure was never recordable.** When pytest fails, `&&` short-circuits, so
   `cd ..` never runs and the `||` branch tries to exec `scripts/record_test_status.py`
   *from inside the package directory*, where it does not exist. It crashes with
   `No such file or directory`. **The mechanism that feeds test outcomes into the
   anchored evidence chain could only ever write `pass`.**
2. **The suite silently truncated.** That crash aborted `make test` at the first failing
   package. One `bcc_middleware` failure meant `integrity-userapi` and
   `integrity-dashboard` **never ran at all** — while the output looked like a single
   ordinary test failure.

The direction of bug 1 is what makes it critical rather than annoying. An evidence
system that can record success and cannot record failure does not have a logging gap;
it has a bias. It is also a direct contributing cause of **F5** — leaves say
`unverified` partly because the recorder feeding them is broken on exactly the path
that matters.

**The trap in fixing it:** repairing only the path makes `|| $(TEST_STATUS) pkg fail`
exit 0, so `make test` would report **success on a red suite** — strictly worse than the
crash it replaced. The fix is `|| { $(TEST_STATUS) pkg fail; false; }` with `$(CURDIR)`
on the recorder: record the outcome, then still fail.

### E16 — The evidence-linkage tests silently dropped the thing they assert on. *(high, fixed)*

`tests/test_evidence_linkage.py` passed in one run and failed in the next with no code
change between them. Not flakiness in the usual sense — a real defect in how the audit
report is dispatched, surfaced by the test setup.

`main._report_decision_background` schedules the audit write as
`asyncio.ensure_future(asyncio.to_thread(report_decision, …))` and **nothing ever awaits
it**. The test's `client` fixture returned a bare `TestClient(app)`, which starts and
tears down a *fresh portal event loop around each request* — so the pending task was
cancelled at teardown before it could run, and the decision row was simply lost. The
test then asserted against an empty list. Measured: 1 pass / 3 fail across four
consecutive runs before the fix, 4/4 pass after (context-managed client, one loop for
the whole test).

**The production shape this exposes is the real finding, and it is not a test artifact.**
Audit reporting is fire-and-forget with no await, no completion signal, and no retry. A
worker that shuts down with reports in flight drops them, silently — the same failure the
test was accidentally reproducing. Under uvicorn the loop is long-lived so it usually
wins, which is precisely why this would not show up until a restart under load. The
`_audit_report_tasks` set in `main.py` prevents *garbage collection* of those tasks; it
does not make anything wait for them. Recorded as open — the test is fixed, the
shutdown-drop is not.

### E2 — The liveness probe reports healthy while the service is fully broken. *(high)*

```

```

`/healthz` answers `200 ok` and touches none of the dependencies whose failure
produces E1. So the single signal an orchestrator, uptime monitor, or load

This is the same class as F10 in the 2026-07-30 audit — a control that exists,

### E4 — Server errors are opaque and uncorrelatable. *(medium)*

Every 500 returns exactly `{"error":"internal server error"}` — 33 bytes, no
request id, no correlation id, no error class. Response headers carry only CORS,
`content-type`, `date`, `vary`.

So a caller — the dashboard, the SDK, an operator, or this audit — can observe
*that* the oracle is failing and nothing whatsoever about *why*. Diagnosis
requires shell access to the container. When shell access is what is unavailable
(as here, and as in the session that produced `HANDOFF.md`), the system becomes
undiagnosable from outside.

Not a request to leak stack traces to clients. A correlation id in the response,
matched to a logged error, gives triage a handle while disclosing nothing.

`docs/INTERFACE_CONTRACT.md` alongside the ports.

### E9 — Two Merkle implementations use **incompatible odd-node conventions**, both claiming to match `StateAnchor` bit-for-bit. *(critical, by reading)*

| | `bcc_middleware/app/merkle.py:95-100` | `integrity_sdk/vault.py:61-63` |
|---|---|---|
| Odd node | **duplicated** — `_hash_pair(level[-1], level[-1])` | **promoted unchanged** |
| Claims | "OpenZeppelin-standard … matches `integrity-oracle`'s `merkle.rs` and `contracts`' `StateAnchor.sol` **bit-for-bit**" | "matching `StateAnchor.verifyLeaf`" |

They cannot both be right. Both cite `docs/INTERFACE_CONTRACT.md` §4.4 as
authority; §4.4 pins the hash function and the sorted-pair rule, and
`merkle.py:17-26` admits in its own INTEGRATION FLAG that the leaf *payload* was
never pinned cross-package.

**The disagreement is not cosmetic — one side documents the other as a forgery
vector.** `vault.py:49-52`:

> duplicating it … makes a tree with leaves [A, B, C] verify a proof for a
> non-existent fourth leaf equal to C, which is a real forgery vector, not a
> style choice.

That reasoning is sound, and it is the known objection to duplicate-last-node
Merkle trees. If it holds, `bcc_middleware` — the component that anchors **BCC
commitments**, the protocol's behavioral evidence — is the one carrying the
vector, while labelling it the standard.

**Why this stayed hidden:** the two conventions produce *identical* roots whenever
every level has even width. They diverge only on odd levels, so passing tests on
power-of-two batches prove nothing. The agent's own vault holds **21 leaves** — odd.

### Ground truth, resolved by reading (was open above)

There are **three** implementations, not two, and the vote is 2–1:

| Implementation | Odd node |
|---|---|
| `integrity-oracle/backend/src/merkle.rs:92-96` | **duplicate** — with a test pinning it (`odd_leaf_count_duplicates_last_node_…`) |
| `bcc_middleware/app/merkle.py:95-100` | **duplicate** |
| `integrity-sdk/integrity_sdk/vault.py:61-63` | **promote** |

`integrity-cli` has no Merkle module (checked) — the CLI's independent
reimplementation does not extend here.

**The root cause is spec silence, not a bad implementation.**
`StateAnchor.sol:12-23` pins exactly two rules — keccak256 leaves, sorted-pair
parents — and says **nothing** about odd nodes. So all three implementations are
honestly compliant with §4.4 as written, and all three claims of matching
"bit-for-bit" are simultaneously true and unfalsifiable. Fixing three files
without amending §4.4 guarantees a fourth divergence later.

**Severity correction: latent, not live.** Two prior open questions are now
answered, both benignly:

- **No clobbering.** `StateAnchor.sol:31-35` keeps `isAnchoredRoot` permanently
  and `rootAtEpoch` as history; `verifyLeaf(root, leaf, proof)` takes an
  **explicit** root, and `submitZkAttestation` passes one. Multiple writers
  anchoring to one `StateAnchor` therefore do **not** invalidate each other's
  proofs. Only `verifyLeafAtLatest` depends on who anchored last.
- **Each system is internally self-consistent.** The vault builds, anchors, and
  proves with its own promote-convention helpers (`vault.proof_for`);
  bcc_middleware and the oracle do likewise with duplication. `prover.py`
  generates ZK proofs and builds no Merkle path. Nothing is broken *today*.

The hazard is the first cross-system verification — any consumer proving a leaf
against a root a *different* component anchored. That is precisely what
"standardize so we can derive conclusions from the data" requires, so this must
be fixed before, not after, coverage work.

### Which convention is actually safer — stated precisely

Both code comments overstate their case, in opposite directions.

Duplication's real property, verified by hand: `[A,B,C]` builds
`H(H(A,B), H(C,C))`, and `[A,B,C,C]` builds the **identical** root. So the root
does **not** uniquely determine the leaf list. That directly contradicts
`StateAnchor.sol:22-23`'s own claim that "the root is a true function of the *set*
of leaves" — the contract's NatSpec is false under the convention 2 of 3
implementations use. This is the classic Bitcoin CVE-2012-2459 shape.

But `vault.py:49-52`'s stronger claim — that duplication lets a tree "verify a
proof for a non-existent fourth leaf" — **overstates it**. The leaf so proven is
`C`, which genuinely is in the tree. Duplication permits root/leaf-list
ambiguity and inflated leaf counts; it does **not** permit proving a leaf that was
never committed. Conversely `merkle.rs:92-96`'s claim that promotion is
"second-preimage-vulnerable" is loose — promotion's real weakness is
leaf/internal-node confusion, which domain-separated leaf preimages fix, and
which `vault.py:118` already has (`"integrity.vault.commit.v1|…"`) while
`merkle.rs::telemetry_leaf_data` and `merkle.py::leaf_hash` do **not**.

Neither side is simply right. See `docs/design/merkle-standardization.md` for the
resulting amendment.

## Hypothesis, not yet a finding: F5 may be structurally unclosable

Open item #1 from the previous audit is "`test_result_hash` is `unverified` on
all 21 anchored leaves." `HANDOFF.md:11` advises committing first. Reading both
scripts suggests **no ordering can work**, which would reframe F5 from a
discipline problem into a design bug.

`scripts/vault_commit_leaf.py:39-63` fingerprints the tree as
`HEAD ‖ git diff HEAD ‖ untracked files`, and `:89-90` marks a leaf
`unverified:stale` unless the recorded fingerprint matches exactly.

- A test run recorded **pre-commit** fingerprints old HEAD + a dirty diff.
- The post-commit hook then checks **new HEAD + an empty diff**.

These can never be equal. Testing after the commit fares no better — the leaf is
already written. `.integrity-test-status` is gitignored and `:53` uses
`--exclude-standard`, so the status file itself is not the perturbation.

**Unverified.** Confirming it needs `make test` → commit → read the leaf, which
needs a shell. Predicted result: `unverified:stale`.

> **CONFIRMED (2026-07-31, with a shell).** The prediction was correct. Reading the
> real vault — 21 leaves for `did:integrity:68fed1…` — **21/21 carry a
> `test_result_hash` of `unverified` or `unverified:stale`**, and the split matches the

> all), and **every one of the remaining 17 is `unverified:stale`** — the fingerprint
> mismatch, not an absence.
>
> Not one leaf in the entire history has ever achieved a verified status. That promotes

> This is what the importer's standing warning refers to — all 21 evidence nodes attest

If confirmed, the fix is to key status to *tree content* rather than `HEAD+diff`:

`record_test_status.py` and `vault_commit_leaf.py:39` must change **together** —
the comment at `:40-41` already warns they must match exactly.

## Open architectural questions this pass adds

1. **What signal proves the stack is serving, not merely running?** E1 and E2 are
   one question wearing two hats. `/healthz` was true and useless. The previous
   audit asked "what makes a build the deployed build?"; this adds "what makes a
   running service a working one?" — and neither has an answer in the repo today.

2. **Should the fail-open gate have a ceiling?** The fail-open posture is
   ratified and this audit does not reopen it. But E3 shows the middleware can be
   down indefinitely while the accounting that makes it visible lives in a log
   nobody reads until an audit. Does a sustained fail-open streak warrant
   escalation — a louder signal, a refusal threshold — or is a lifetime ratio
   genuinely enough?

3. **Can the system be diagnosed without a shell?** E4 says no, and this session
   is the proof: a total functional outage was detectable from outside but not
   explainable from outside. That is an operability property worth choosing
   deliberately.
